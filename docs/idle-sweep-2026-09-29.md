## 해석

- **Claude Code**: 대조군도 1시간까지 95.7~98.4%를 읽었습니다. 사용 기록에는 1시간
  캐시 쓰기가 남았고, 2시간 대조군은 약 21%로 떨어졌습니다. 1시간 이하에서는 유지
  요청의 추가 비용만 커졌습니다(+47~+904%). 2시간 쌍은 대조군이 대화를 다시 써야
  해서 차이가 +38~+42%로 작았습니다.
- **Codex**: 대조군이 1시간까지 99.5~99.6%를 읽어 cachemax의 차이가 없었습니다.
  2시간에는 대조군이 0%와 15.2%로 떨어졌고 사용군은 99.5%였습니다. 입력은 유지
  횟수에 비례해 1.7~47.3배로 늘었습니다.
- **Grok Build**: 대조군은 5·10분에는 적중했지만, 15분부터 8회 중 7회가 0~21.6%만
  읽었습니다. 사용군은 12개 쌍 모두 99.7~99.9%였습니다. 대조군이 놓친 쌍에서는 첫
  표시가 사용군에서 0.6~2.8초 빨랐지만, 비용 추정치는 모든 쌍에서 늘었습니다.

## 방법과 한계

- 호스트·시간마다 2쌍입니다. 한 쌍은 대조군을, 다른 쌍은 사용군을 먼저 준비했습니다.
  각 세션에 같은 1,500행 합성 자료와 다른 확인 문자열을 넣고, 예열 요청 1회를 마친
  시점부터 실제 시계로 유휴 시간을 셌습니다. 사용군은 기본 3분 간격으로
  `Only ".". No tools.`를 보냈고, 대조군은 중간 요청이 없습니다. 마지막 요청은
  확인 문자열을 회상시켜 같은 세션인지 검사했습니다.
- Claude Code 2.1.284(`claude-opus-5-5[1m]`), Codex 0.158.0(`gpt-6-astra`),
  Grok Build 1.0.41(`grok-4.7`), Node 26.7.0, macOS에서 실행했습니다. 같은 배치의
  조건은 한 컴퓨터·호스트별 한 계정에서 동시에 돌았습니다. 공유된 호스트 문맥 캐시가
  대조군 결과에 섞였을 수 있습니다.
- 배치는 세 번입니다. 배치 a는 시작 약 10분 뒤 다른 세션이 `~/.claude/settings.json`을
  편집해 설정 검사에 걸렸고, 5분 조건만 남기고 중단했습니다. 이후 각 호스트가 자기
  설정 파일만 검사하도록 고치고 10분~2시간을 배치 b로 다시 실행했습니다. 배치 b의
  Codex는 다른 세션의 `~/.codex/config.toml` 추론 강도 편집으로 무효가 되어, Codex
  6개 조건을 배치 c에서 같은 설정으로 모두 다시 실행했습니다. Claude 5분은 설정 편집
  전 배치 a의 결과입니다. 측정된 결과를 교체하려고 다시 실행한 적은 없습니다.
- 기존 측정 도구는 유지 요청 수가 `ceil(유휴/간격) - 1`과 정확히 같아야 했습니다.
  대기는 직전 응답 뒤부터 세므로 2시간 조건에서는 마지막 예정 요청이 마감 뒤로
  밀립니다. Grok 2시간 두 쌍은 38회로 이 검사에서만 실패했고, 1회 이상·계획 이하로
  고친 규칙과 나머지 모든 검사를 저장된 자료에서 통과해 유효로 다시 판정했습니다.
  원자료에 원래 오류와 재판정 사유를 함께 남겼습니다.
- 이번 작업의 완료된 모델 요청은 중단·무효 배치를 포함해 982회입니다. CLI 달러 값은
  구독 청구액이나 분리된 구독 한도 소모량이 아닙니다. 2쌍으로 적중 확률을 추정하지
  않았고, 실제 절전·깨우기는 검사하지 않았습니다.

# 캐시 개선 추가 분석 — 2026-09-25

이 문서는 기존 로그의 재분석입니다. 이후 수행한 세 플랫폼 공통 조건의
실제 54회 재측정은 [재관측 보고서](reproducibility-report.md)에 별도로 기록했습니다.

Codex에서 확인한 개선은 **다음 사용자 요청의 캐시 읽기 비율 상승**입니다.
원본 로그를 더 살펴보니 24개 세션 중 20개에서 최초 응답 후 스킬 지시문이 추가됐습니다.
유지 요청이 이 추가 입력을 미리 처리하는 효과가 섞여 있어, 기존 결과만으로
순수한 캐시 만료 방지 효과나 총사용량 절감을 분리해 입증할 수 없습니다.

이 재분석은 기존 대조 실험 30쌍, 장시간 유지 요청 79회, Codex 원본 세션 24개를
다시 관측·계산했습니다. 새 모델 요청은 보내지 않았습니다. 데이터 수집 시점은
기존 검증과 같으며, 독립적인 새 실험이나 표본 수 증가로 계산하지 않습니다.
기존 실행 파일·계정 설정·설치본·배포 압축 파일은 변경하지 않았습니다.

계산 결과는 [추가 분석 JSON](cache-analysis.json), 지시문 감사 결과는
[내용을 제외한 원본 로그 요약](codex-prefix-audit.json)에 있습니다.
기존 원자료 [measurements-0.1.1.json](measurements-0.1.1.json)은 그대로 보존했습니다.

다음 표는 각 쌍의 **사용군 − 대조군** 차이를 먼저 구한 뒤 중앙값을 계산한 것입니다.
95% 기준은 높은 캐시 읽기를 구분하기 위한 분석상 기준이며, 공급자의 적중 보장이 아닙니다.
입력 배수에는 최초 데이터 입력 이후의 유지 요청과 마지막 사용자 요청을 모두 포함합니다.

| 조건: 유휴 / 유지 간격 | 다음 요청 캐시 비율 차이 | 다음 요청 95% 이상: 대조 / 사용 | 총입력 배수 중앙값 | 첫 표시 지연 차이 | 더 빠른 쌍 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Claude 70분 / 50분 | −0.019%p | 0/6 → 0/6 | 2.001배 | −0.093초 | 4/6 |
| Codex 35분 / 9분 | +15.60%p | 2/6 → 5/6 | 4.004배 | −0.503초 | 4/6 |
| Codex 70분 / 25분 | +15.73%p | 0/6 → 6/6 | 3.000배 | −0.253초 | 5/6 |
| Grok 12분 / 3분 | +0.030%p | 5/6 → 4/6 | 4.005배 | +0.550초 | 3/6 |
| Grok 70분 / 25분 | +2.65%p | 0/6 → 2/6 | 3.003배 | −0.505초 | 4/6 |

캐시가 늘어난 경우에도 속도가 항상 빨라지지는 않았습니다. Codex 35분의 쌍별 첫 표시
지연 차이는 −2.394~+1.356초, 70분은 −0.905~+0.262초입니다. 기존 보고서의
“각 군 중앙값끼리의 차이”와 위 표의 “쌍별 차이의 중앙값”은 다른 통계량입니다.
같은 계정·시간대의 요청들이 겹쳤고 조건별 표본도 6쌍이므로 독립성이나 통계적
유의성을 가정하지 않았습니다. 70분의 6/6 높은 적중은 해당 관측 결과이지 보장 확률이 아닙니다.

가장 큰 추가 발견은 **Codex의 유휴 구간 전후에 입력 형태가 같지 않았다는 점**입니다.
원본 JSONL의 `task_started`를 기준으로 각 턴의 developer `skills_instructions`
블록을 검사했습니다. 스킬 목록은 206개에서 225개로, 경로 별칭은 13개에서 16개로
바뀌었습니다. 블록의 길이는 22,196자와 22,198자로 비슷하지만 SHA-256은 달랐습니다.
단순 문자열 길이 검사는 이 변화를 놓칩니다.

| 관측 | 35분 실험 | 70분 실험 |
| --- | ---: | ---: |
| 감사한 세션 | 12 | 12 |
| 최초 응답 후 갱신된 스킬 블록이 추가된 세션 | 9 | 11 |
| 최초 턴부터 갱신된 목록이 있었던 세션 | 3 | 1 |
| 대조군의 최초 후속 입력 증가 중앙값 | 6,733토큰 | 6,739.5토큰 |

이는 호스트가 제공한 문맥의 변화를 직접 확인한 결과입니다. 왜 첫 턴부터 전체
목록을 받은 세션과 나중에 받은 세션이 생겼는지는 확정하지 않았습니다.
목록 로딩 시점과 관련됐을 가능성은 있지만, 이를 공급자 내부 라우팅 원인으로
단정할 근거는 없습니다. 이 감사는 로컬 기록의 지시문 블록을 검사하며 실제 전송
요청 전체나 숨겨진 서버 문맥이 동일했음을 보장하지 않습니다.

70분 실험의 `trial: 0`을 보면 구조가 분명합니다.

| 요청 | 입력 토큰 | 캐시 읽기 토큰 |
| --- | ---: | ---: |
| 대조군 최초 입력 | 36,315 | 0 |
| 대조군 마지막 사용자 요청 | 43,054 | 36,096 |
| 사용군 최초 입력 | 36,313 | 17,280 |
| 사용군 첫 유지 요청 | 43,046 | 36,096 |
| 사용군 두 번째 유지 요청 | 43,063 | 42,880 |
| 사용군 마지막 사용자 요청 | 43,086 | 42,880 |

대조군도 최초 입력 크기에 가까운 36,096토큰을 다시 읽었습니다. 사용군은 첫 유지
요청에서 늘어난 입력을 먼저 처리했고 이후 더 긴 입력을 재사용했습니다.
이 쌍의 비캐시 입력 합계는 사용군이 오히려 **381토큰 더 많습니다**.
따라서 마지막 요청의 약 83.8% → 99.5% 상승을 모두 “70분 동안 캐시를 지켰다”로
해석하면 과장됩니다. 입력을 미리 처리한 효과가 상당 부분 섞였다는 해석을 뒷받침합니다.
캐시 재사용이 렌더링된 입력 앞부분의 일치에 의존한다는 원리는
[OpenAI 공식 캐시 문서](https://developers.openai.com/api/docs/guides/prompt-caching)에 설명돼 있습니다.

기존 환경 검사 [fingerprint](../tests/validation-support.mjs)는 실행 파일 해시,
CLI 버전, 설정 파일 크기·수정 시각을 검사합니다. **동적으로 추가된 스킬 지시문은
그 검사 대상이 아닙니다.** 기존의 환경 고정 검사 통과는 유지하되, 프롬프트 문맥까지
통제됐다는 의미로 확대할 수 없습니다.

유지 요청을 포함한 Codex 입력량도 별도로 계산했습니다. Codex의 `inputTokens`에는
캐시 읽기가 포함되므로, 비캐시 입력은 `inputTokens − cacheReadTokens`입니다.
Claude·Grok의 전체 입력은 일반 입력 + 캐시 읽기 + 캐시 쓰기로 계산했습니다.
출력에 이미 포함된 reasoning 토큰을 출력에 다시 더하지 않았고, 없는 지표는 `null`로 남겼습니다.

| Codex 조건, 6쌍 합계 | 대조군 | 사용군 | 변화 |
| --- | ---: | ---: | ---: |
| 35분: 전체 입력 | 245,524 | 1,008,500 | +762,976 |
| 35분: 비캐시 입력 | 28,436 | 117,876 | +89,440 |
| 35분: 캐시 읽기 | 217,088 | 890,624 | +673,536 |
| 70분: 전체 입력 | 258,303 | 755,874 | +497,571 |
| 70분: 비캐시 입력 | 96,639 | 37,282 | −59,357 |
| 70분: 캐시 읽기 | 161,664 | 718,592 | +556,928 |

35분 조건은 전체 입력으로 가중한 캐시 비율도 **88.42% → 88.31%**입니다.
마지막 사용자 요청만 보면 약 99.5%지만, 그 지점까지의 유지 요청을 포함하면
입력 재사용 효율이 개선됐다고 보기 어렵습니다. 사용군 마지막 요청이 캐시 읽기 0인
쌍도 1개 있으며, 유지 요청까지 포함하면 사용군의 읽기 0 요청은 2개입니다.

12쌍 중 9쌍에서 사용군의 비캐시 입력과 캐시 읽기가 모두 늘었습니다.
이 9쌍은 두 입력 종류에 양의 가중치를 부여하는 계산에서 입력 부담이 줄지 않습니다.
이것은 입력 측면의 판정이며, 출력 비용·쓰기 요금·구독 한도까지 포함한 청구 판정은 아닙니다.

70분 합계의 비캐시 입력 감소는 큰 미적중을 겪은 대조군 2개가 주도합니다.
가정상 입력 부담을 `U + r × C`로 두면, `U`는 비캐시 입력, `C`는 캐시 읽기,
`r`은 두 입력의 상대 가중치입니다. 70분 합계의 손익분기점은
`59,357 / 556,928 = 0.10658`입니다. 출력과 알 수 없는 캐시 쓰기 할증을 제외한
민감도 계산이며 실제 모델 가격이나 구독 사용량 공식으로 사용하지 않습니다.

| 가정: 캐시 읽기 가중치 r = 0.10 | 35분 | 70분 |
| --- | ---: | ---: |
| 6쌍 합계 입력 부담 변화 | +312.68% | −3.25% |
| 쌍별 변화의 중앙값 | +281.42% | +84.27% |
| 입력 부담이 줄어든 쌍 | 0/6 | 2/6 |

70분에서 합계만 보면 조금 좋아져도, 전형적인 쌍의 부담은 늘어납니다.
또 가장 크게 줄어든 `trial: 3`은 사용군에만 최초부터 갱신된 스킬 목록이 있었으므로
입력 구조의 비대칭도 있습니다. 이 자료로 구독 비용 절감을 주장하거나
25분 간격을 최적값으로 정할 수 없습니다. 최신 API 문서는 모델별 읽기·쓰기 요금과
TTL을 구분하지만, 그 정책을 이번 구독 CLI 경로에 그대로 적용할 근거도 수집되지 않았습니다.
[OpenAI 공식 캐시 문서](https://developers.openai.com/api/docs/guides/prompt-caching)

장시간 기록은 유지 요청의 성공과 실제 캐시 읽기를 구분해서 볼 필요가 있습니다.
아래는 2시간 동안 발생한 **유지 요청만** 합산했으며 최초 입력·후속 회상은 제외했습니다.

| 플랫폼 | 완료 | 캐시 읽기 0 | 입력 가중 캐시 비율 | 전체 입력 | 첫 유지 → 마지막 유지 입력 증가 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Claude | 2/2 | 0 | 36.71% | 66,237 | +551토큰 |
| Codex | 39/39 | 0 | 98.61% | 1,048,950 | +711토큰 |
| Grok | 38/38 | 15 | 60.31% | 1,571,807 | +1,855토큰 |

Codex는 캐시 읽기가 안정적이지만 유지에만 약 105만 입력 토큰을 처리했습니다.
이는 구독 한도가 105만만큼 줄었다는 뜻이 아닙니다. Grok은 3분 간격에서도 39.5%가
캐시 읽기 0이어서, 간격을 짧게 하는 것만으로 지속적인 적중을 보장하지 못했습니다.
유지 요청의 CLI 비용 추정치는 Claude 약 $0.3403, Grok 약 $0.5871이며 Codex는 없습니다.
대조군이 없는 장시간 기록으로 절감 효과를 산출하지 않았습니다.

숨김은 화면에서만 적용됩니다. 원본 대화에는 유지 턴이 남고 이후 입력에도 누적됩니다.
그 결과 위 표처럼 요청당 입력이 커집니다. “점 하나를 보냈다”는 사실로 요청 전체의
입력량이나 reasoning·출력 사용량이 작다고 판단할 수 없습니다.

Claude의 70분 실험은 양 군 마지막 요청의 캐시 읽기가 모두 12,160토큰이고,
사용군의 추가 유지 요청에서도 약 4.3만 토큰의 새 쓰기가 발생했습니다.
별도 기존 진단인 `claude-stream-probe.json`과 `claude-variants.json`에서도
동일 프로세스 사용 또는 설정 축소 후 새 쓰기가 반복됐습니다. 1시간 쓰기 카운터는
확인됐지만 쓰기 TTL만으로 다음 턴의 적중을 설명할 수 없습니다. 실제 요청 앞부분의
동일성·캐시 경계를 확인하는 것이 다음 진단 순서이며, 정확히 어떤 필드가 문제인지까지는
확인하지 못했습니다. [Claude Code 캐시 문서](https://code.claude.com/docs/en/prompt-caching)는
앞부분 일치와 요청별 TTL을 별개로 설명합니다.

Grok의 70분·25분 조건은 **유지 요청 12개 모두 캐시 읽기 0**이었습니다.
마지막 사용자 요청에서만 2개는 약 99.7%, 1개는 약 5.3%였습니다. 마지막 적중 사례만
선택하면 유지 과정의 비용을 놓치게 됩니다. 12분·3분에서도 마지막 높은 적중은
대조군 5/6, 사용군 4/6이므로 일관된 개선이 아닙니다. 기존 CLI 비용 추정치 증가는
각 조건 중앙값 +197.8%, +591.8%로 유지됩니다. 서버 라우팅·퇴거는 가능한 설명이지만
실제 요청 헤더를 관측하지 않아 원인으로 확정하지 않았습니다.
[xAI 공식 문서](https://docs.x.ai/developers/advanced-api-usage/prompt-caching/best-practices)는
같은 대화로 라우팅하더라도 서버 부하·재시작 등으로 캐시가 사라질 수 있다고 설명합니다.

실행 코드의 상태 표시도 해석 범위를 좁혀야 합니다.
[Keeper.execute](../plugins/cachemax/scripts/core.mjs)의 `cache_observed`는
해당 요청의 `cacheReadTokens > 0`이라는 뜻입니다. 전체 문맥 적중, 다음 요청의 적중,
비용 절감, 서버 TTL 확인을 뜻하지 않습니다. 현재 `--ttl`은 로컬 유지 간격을
검사하기 위한 값이며, 어댑터가 공급자에게 캐시 TTL 설정을 전달하는 옵션이 아닙니다.
검증 없는 TTL 자동 추정이나 유지 빈도 증가는 이번 분석에서 추가하지 않았습니다.

후속 실측은 아래 순서가 정보 대비 비용이 가장 작습니다. 아직 실행한 결과는 아닙니다.

1. Codex 양 군 모두 최초 대화와 스킬 목록이 안정된 뒤 같은 예열 절차를 거치고
   유휴 시간을 시작합니다. 최초·예열·후속 턴의 지시문 해시와 입력 증가를 기록하고,
   입력 형태 불일치를 효과 판정에서 분리하는 기준을 실험 전에 정합니다.
2. 조건을 고정한 35분 대조 실험부터 반복합니다. 관측용 중간 요청은 대조군의 캐시를
   데우므로 보내지 않습니다. 0회 유지와 1회 유지를 먼저 비교하고, 실제 결과가
   필요성을 뒷받침할 때 유지 횟수·유휴 시간을 늘립니다.
3. 처음 입력부터 마지막 요청까지 모든 사용량, 각 유지 요청의 읽기·쓰기·출력,

   Grok은 동일 세션 인계와 라우팅 식별자 전달을 확인합니다. 인증 정보나 원문을

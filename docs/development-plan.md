# Cache Keeper — Loop 기반 플러그인 개발 계획

> **목표:** Claude Code · Codex · Grok Build의 기존 세션에 아주 짧은 프롬프트를 반복 전송하되, 사용자 화면에는 유지용 요청과 `.` 응답이 나타나지 않게 한다. 사용자는 마지막 실제 답변 바로 아래에서 작업을 이어간다.
>
> **작성·공식 문서 확인:** 2026-09-24  
> **상태:** 개발 설계안. 실제 CLI·계정에 연결한 구현 및 통합 테스트는 아직 수행하지 않았다. 아래 명령·설정·인터페이스는 별도 표시가 없는 한 **개발할 제품의 제안 사양**이다.

---

## 1. 핵심 결정

| 항목 | 결정 |
| --- | --- |
| 캐시 유지 방식 | 세 도구 모두 **동일 세션에 최소 프롬프트를 반복 전송하는 loop** |
| 기본 프롬프트 | `Only ".". No tools.` |
| 기대 응답 | `.` |
| 사용자 화면 | 유지용 입력·응답을 모두 숨기고 마지막 실제 대화를 유지 |
| 내부 대화 기록 | 유지용 턴도 원본에 남긴다. 삭제·되감기하지 않는다 |
| 패키징 | 플랫폼별 플러그인 + 공통 로컬 실행기 + 필요한 경우 얇은 대화 화면 |
| 실행 엔진 | 네이티브 `/loop`가 요구 조건을 만족하면 사용. 아니면 같은 세션을 호출하는 로컬 `LoopRunner` |
| 기본 유지 기간 | 사용자가 입력한 시간. `2h`는 활성화 시점부터 정확히 2시간의 **실행 허용 구간** |
| 사용자 복귀 | 유지 요청보다 실제 입력을 우선 처리. 이후에도 원래 종료 시각까지만 유지 |
| 성공 판정 | 요청 성공과 캐시 적중을 구분. 가능하면 **다음 실제 사용자 요청**의 캐시 사용량으로 검증 |

### 반드시 구분할 것

**“화면에서 안 보임”과 “모델의 대화 기록에 없음”은 다르다.** 이번 버전은 전자를 구현한다. Loop가 실제 턴을 만들기 때문에 후자까지 동시에 보장하지 않는다.

또한 “loop 방식”을 “세 제품 모두 동일한 내장 `/loop` 명령 사용”으로 해석하지 않는다. Claude Code와 Grok Build에는 내장 반복 기능이 확인되지만, 확인한 Codex CLI 명령 목록에서는 동등한 `/loop`를 찾지 못했다. Codex는 자체 타이머와 App Server를 연결한다.[^claude-loop][^grok-loop][^codex-commands][^codex-server]

**단순 플러그인 설치만으로 세 제품의 기존 기본 화면을 모두 완벽하게 제어한다고 약속하지 않는다.** 완전한 숨김이 필요한 경로에는 Cache Keeper가 소유하는 표시 계층을 사용한다.

### 이번 버전에서 하지 않음

API 요청 재작성 프록시, `max_tokens: 0`, prewarm API, prefix 재배치, 토큰 추출, 계정 간 라우팅은 사용하지 않는다. 기존 인증과 기존 세션 실행 경로를 유지한다.

24시간 무제한 실행, 운영체제 절전 방지, 대화 기록 자동 청소, 다른 제품의 기본 UI까지 숨김 상태 동기화, 캐시 적중률·비용 절감 보장도 범위 밖이다.

## 3. 플랫폼별 근거와 구현 선택

아래는 **공식 문서에서 확인한 인터페이스**와 **이 프로젝트에서 선택할 설계**를 분리한 표다.

| 플랫폼 | 확인한 기능 | 구현 선택 | 먼저 검증할 부분 |
| --- | --- | --- | --- |
| Claude Code | `/loop` 및 cron 기반 반복 실행[^claude-loop] | 네이티브 loop 어댑터 구현 | 예약 요청 식별, 실행 직전 차단, 종료 처리 |
| Claude Code | `MessageDisplay`로 assistant 표시 텍스트 변경 가능. 입력·도구 결과는 대상 아님[^claude-hooks] | 응답 숨김에 활용하되 완전한 화면 제어는 별도 경로 준비 | 빈 응답 행, 입력 표시, 재렌더링, 훅 실패 시 원문 노출 |
| Claude Code | 구조화된 출력과 세션 ID를 이용한 resume[^claude-headless] | 필요 시 관리형 실행기와 화면의 연결 경로로 사용 | 같은 세션·설정 보존 및 기존 대화 인계 |
| Codex | App Server의 `thread/resume`, `turn/start`, `turn/interrupt`, 스트리밍 이벤트[^codex-server] | 로컬 loop + App Server + 자체 표시 필터 | 턴 식별자 연결, 취소 완료, 이력 재표시 |
| Codex | 플러그인 훅 지원. `suppressOutput`은 표시 숨김 기능으로 사용할 수 없는 상태[^codex-hooks] | 훅은 제어·관측에 사용. 숨김은 렌더러에서 처리 | 설치 버전의 훅·도구 차단 범위 |
| Grok Build | `/loop`; 첫 실행은 즉시 발생하고 이후 반복[^grok-loop] | 네이티브 loop 어댑터 구현 | 최초 호출 과금, 예약 요청 식별, 종료 처리 |
| Grok Build | ACP의 `session/prompt`, `session/update`; headless의 세션 resume·구조화된 출력[^grok-headless] | 완전한 숨김에는 ACP 기반 화면을 우선 검증 | 기존 세션 로드, 완료 경계, 후행 이벤트 |
| Grok Build | 훅·플러그인 지원. `Stop`은 수동 알림이며 표시 제어 훅이 아님[^grok-hooks][^grok-plugins] | 훅은 상태·도구 제어에 제한해 사용 | 네이티브 화면 전체 숨김을 가정하지 않음 |

### 실행 모드

**`managed-quiet`: 기본 제품 경험**

Cache Keeper가 세션의 입력·출력을 소유한다. 화면은 실제 대화만 렌더링하고, 반복 실행은 로컬 `LoopRunner` 또는 검증된 네이티브 스케줄러에 맡긴다. 유지용 턴이 화면에 한 번 나타난 뒤 지워지는 것이 아니라 **처음부터 렌더링되지 않아야 한다.**

**`native`: 조건부 호환 모드**

기존 CLI 화면과 네이티브 `/loop`를 최대한 유지한다. 다만 입력·응답 숨김, 신뢰할 수 있는 턴 식별, 종료 직전 차단을 모두 통과한 버전만 완전 숨김 지원으로 표시한다. 지원이 부족하면 자동으로 조용히 진행하지 말고 관리형 경로가 필요함을 안내한다.

**`--require-native-loop`: 진단용 엄격 옵션**

내장 `/loop`만 허용한다. 해당 인터페이스가 확인되지 않은 Codex 환경에서는 활성화를 거절한다. 로컬 타이머를 내장 기능이라고 표시하지 않는다.

## 4. 사용자 경험

### 4.1 제안 명령

아래 슬래시 명령은 **Cache Keeper의 공통 화면에서 제공할 명령**이다. 각 제품의 기본 CLI에 동일한 문법이 이미 있다는 뜻은 아니다. 네이티브 플러그인은 해당 호스트의 스킬·명령 체계로 연결한다.

```text
/cache-keeper 2h
/cache-keeper off
/cache-keeper status
/cache-keeper logs
/cache-keeper show-hidden
```

공통 로컬 실행기에는 다음 진입점을 제안한다.

```bash
cache-keeper run claude
cache-keeper run codex
cache-keeper run grok

cache-keeper on --session <id> --duration 2h
cache-keeper off --session <id>
cache-keeper status --session <id>
```

`on --session`은 **이미 Cache Keeper가 소유하거나 안전하게 인계받은 세션**만 받는다. 임의의 실행 중인 CLI에 두 번째 작성자로 붙지 않는다.

### 4.2 활성화 시 한 번만 안내

```text
Cache Keeper 켜짐 · 지금부터 2시간 · 대화 숨김 켜짐
반복 요청은 사용량을 소비합니다. 캐시 효과는 관측 가능한 지표로 확인합니다.
```

반복 요청마다 말풍선, `.` 행, 성공 로그, 소리, 데스크톱 알림을 만들지 않는다. 상태를 보여줘야 한다면 기존 상태 영역의 작은 표시만 갱신한다.

### 4.3 사용자가 보는 화면

```text
사용자: 로그인 오류 수정해줘.
에이전트: 수정했습니다. 변경 사항과 테스트 결과는 다음과 같습니다.
          ... 마지막 실제 답변 ...

[한동안 사용자가 자리를 비움 — 화면에는 추가 대화가 나타나지 않음]

사용자: 그럼 테스트도 보강해줘.
에이전트: ... 실제 다음 답변 ...
```

내부 기록은 다음과 같을 수 있지만, 기본 화면에서는 유지용 턴을 제외한다.

```text
실제 사용자 → 실제 답변
유지용 입력 → .
유지용 입력 → .
실제 사용자 → 실제 답변
```

### 4.4 복귀 의미

“끝난 대화부터 시작”은 **화면과 입력 위치의 연속성**을 의미한다. 세션을 과거 시점으로 rewind하거나 모델 기록에서 유지용 턴을 삭제하는 동작은 아니다.

다른 기본 CLI나 원본 transcript 뷰어로 같은 세션을 열면 유지용 턴이 보일 수 있다. 숨김 보장은 Cache Keeper가 제어하는 지원 화면에 한정한다.

## 5. 최소 프롬프트 사양

### 기본값

```text
Only ".". No tools.
```

본문은 **19 ASCII 문자·19바이트**다. 기대하는 응답 본문은 `.` 하나다. 문자 수와 토큰 수는 같지 않으며, 모델별 실제 토큰 수와 reasoning 사용량은 별도로 측정한다.

### 선택 이유

`ping`이나 `.`만 보내는 것보다 원하는 출력과 도구 비사용 의도가 명확하다. 반복적으로 긴 “캐시 유지 요청입니다…” 설명을 보낼 필요도 없다. 단, 이 문장은 모델에 대한 요청이지 도구 실행을 기술적으로 막는 보안 장치는 아니다.

### 구현 규칙

- 매회 날짜, 세션 UUID, nonce, 실행 횟수, 로그 설명을 프롬프트에 붙이지 않는다. 식별 정보는 로컬 메타데이터로 처리한다.
- 유지 요청마다 스킬 전체를 재호출하지 않는다. 스킬은 설정·활성화에 사용하고, 실제 tick에는 위 본문만 전달한다.
- 프롬프트를 더 짧게 만들려고 장문의 규칙을 system prompt에 추가하거나 `CLAUDE.md`·`AGENTS.md`를 자동 수정하지 않는다.
- 별도 저가 모델·서브에이전트로 전환하지 않는다. 모델·인증 경로·작업 디렉터리·tools 등은 실제 대화와 일치시키는 것을 원칙으로 한다.

### 응답 검사

```text
response.trim() == "." → 정상 유지 응답
그 외                 → keeper 일시 중지 + 짧은 로컬 경고
```

경고 후 모델에게 “다시 점만 출력해”라는 보정 요청을 반복하지 않는다. 호출 폭주를 막는다. 응답이 정상이어도 이를 cache hit로 판정하지 않는다.

`max_output_tokens=1`처럼 공통으로 검증되지 않은 설정을 강제하지 않는다. 출력 상한을 사용하려면 해당 모델의 reasoning·도구 설정과의 호환성을 먼저 확인한다. 화면에서 숨기는 것만으로 서버의 생성 비용이 없어지지는 않는다.

## 6. 대화 표시와 원본 기록 분리

### 6.1 두 개의 관점

| 구분 | 내용 | 정책 |
| --- | --- | --- |
| 원본 대화 | 호스트가 보관하는 실제 사용자·assistant·유지용 턴 | 호스트에 맡기고 수정하지 않음 |
| 표시용 대화 | 원본 이벤트 중 keeper 소유 턴을 제외한 화면 | 사용자에게 보여줄 목록과 앵커만 관리 |

원본을 삭제하는 대신 표시할 때 다음 조건을 적용한다.

```text
신뢰할 수 있는 로컬 매핑상 keeper가 만든 턴인가?
  예  → 정상 유지용 대화 이벤트는 표시하지 않음
  아니오 / 식별 불가 → 실제 대화로 취급하고 보존
```

식별 실패 시 유지 기능을 중지한다. 사용자의 실제 답변을 잘못 숨기는 것보다 유지용 텍스트가 한 번 노출되는 편이 낫다.

### 6.2 턴 식별

요청 제출 전 `requestKey`와 소유권을 등록하고, 호스트가 반환한 `turnId` 또는 동등한 식별자와 연결한다. 이 필드들은 **플러그인의 내부 필드**이며 미지원 API 매개변수로 전송하지 않는다.

```typescript
interface TurnOwnership {
  host: "claude" | "codex" | "grok";
  sessionId: string;
  requestKey: string;
  hostTurnId?: string;
  source: "user" | "keeper" | "control";
  generation: number;
}
```

API 응답보다 스트리밍 이벤트가 먼저 도착할 수 있는 경로는 이벤트를 잠시 보관한 후 소유권을 연결한다. 시간대나 본문 일치만으로 keeper 턴이라고 추정하지 않는다.

네이티브 `/loop`가 job ID와 실행 턴의 연결을 제공하지 않으면 해당 경로는 완전 숨김 모드에 사용하지 않는다. 프롬프트에 랜덤 식별자를 넣는 방식으로 이를 대체하지도 않는다.

### 6.3 숨김 범위

유지용 입력, 정상 응답의 delta와 최종 본문, 해당 턴의 정상 진행 표시·완료 알림을 함께 숨긴다. 단순히 최종 `.`만 필터링해서 스트리밍 중 잠깐 노출되는 구현은 불합격이다.

예기치 않은 도구 요청, 인증 실패, 사용량 제한, 내부 오류는 “조용히 성공”으로 처리하지 않는다. keeper를 멈추고 짧은 로컬 상태 경고를 표시한다. 보안·오류 알림 전체를 무조건 숨기는 기능은 만들지 않는다.

**금지:** `text === "."`만으로 필터링, 정규식으로 모든 마침표 삭제, ANSI 커서 명령으로 출력 후 지우기, 호스트 JSONL에서 해당 행 삭제.

### 6.4 마지막 실제 답변 유지

`lastVisibleUserMessageId`, `lastVisibleAssistantMessageId`, 스크롤 앵커, 편집 중인 입력을 따로 관리한다. keeper 턴은 이 값들을 갱신하지 않는다.

다음 실제 사용자 요청이 끝나면 새 실제 답변으로 앵커를 갱신한다. 창 크기 변경, 이력 재조회, 세션 재열기에도 같은 필터를 적용한다. Claude의 표시 훅 ID가 transcript ID와 동일하다고 가정하지 않는다.[^claude-hooks]

## 8. Loop 엔진과 타이밍

### 8.1 기본 동작

세션이 유휴 상태이며 요청 시각이 되었을 때만 heartbeat를 보낸다. 사용자 작업 중이거나 입력이 대기 중이면 건너뛴다. 누락된 tick을 몰아서 실행하지 않는다.

`setInterval(async () => ...)`로 중첩 실행하지 말고, 한 번의 실행이 끝난 뒤 다음 시각을 계산하는 단일 스케줄러를 사용한다.

```text
OFF → ARMED → HEARTBEAT → ARMED
               │
               ├─ 사용자 입력 → YIELDING → USER_TURN → ARMED
               ├─ 비정상 응답·오류 → PAUSED
               └─ 종료 시각·수동 중단 → STOPPED

ARMED → USER_TURN → ARMED
```

`ARMED`로 돌아갈 때는 항상 원래 종료 시각을 재확인한다. keeper 응답이나 사용자 활동 때문에 기간을 자동 연장하지 않는다.

### 8.2 반복 간격 정책

다음 값은 **제품의 초기 정책 제안**이지 공급자의 유지 보장값이 아니다.

| 환경 | 초기 정책 |
| --- | --- |
| 실제 적용 TTL이 5분으로 확인된 환경 | 3분 간격을 초기값으로 사용 |
| 실제 적용 TTL이 1시간으로 확인된 환경, 로컬 타이머 | 50분 간격을 초기값으로 사용 |
| 실제 적용 TTL이 1시간인 Claude 네이티브 cron | 지연·간격 변환을 고려해 30분부터 검증 |
| Codex·Grok 등 TTL을 확인할 수 없는 경로 | 3분의 실험 프로필. `TTL unknown` 및 효과 미검증 표시 |
| 종료 시각이 다음 필요 호출보다 빠름 | 유지 요청을 생략하고 예정대로 종료 |

Claude Code의 TTL은 요청·과금 경로에 따라 달라진다. 구독 이름만으로 고정하지 않고, 노출되는 설정·usage 등으로 확인한다.[^claude-cache]

네이티브 Claude 스케줄러에는 지연 오프셋과 유휴 대기가 있으므로 단순히 “4분 loop = 5분 TTL 보장”으로 취급할 수 없다.[^claude-loop]

설계 시 다음 관계를 점검한다.

```text
계획 간격 + 스케줄러 최대 지연 + 네트워크 여유 < 확인된 TTL
```

사용자 작업, 절전, 네트워크 단절로 대기가 무한히 길어질 수 있으므로 이 관계도 유지 보장을 뜻하지 않는다. 실제 공백이 커졌다면 `gap_detected`를 기록하고 hit 상태를 추정하지 않는다.

### 8.3 유지 기간의 엄격한 경계

시작할 때 `expiresAt = activatedAt + duration`을 고정한다. 시간대는 표시용으로만 사용하고 실행 중 경과 시간은 단조 시계를 기준으로 관리한다.

신규 요청을 보내기 **직전**에 종료 시각, 소유권, generation, 횟수 상한을 재확인한다. 취소된 오래된 예약이 큐에 남아도 다시 살아나면 안 된다.

종료 시각 전에 이미 서버에 전달한 요청은 취소를 시도하되, 이미 발생한 사용량을 없앨 수 있다고 표시하지 않는다. 보장할 것은 **종료 이후 신규 유지 요청을 허용하지 않는 것**이다.

네이티브 loop가 실행 직전 검사를 지원하지 않으면 엄격 모드는 로컬 `LoopRunner`로 전환한다. 모델에게 “2시간 뒤 알아서 멈춰”라고 부탁하는 것만으로 종료를 구현하지 않는다.

## 9. 플랫폼별 개발 작업

### 9.1 Claude Code

**네이티브 경로:** `/loop`·cron 관리, 요청 이벤트 관측, `MessageDisplay` 활용을 작은 시제품으로 검증한다. 등록용 관리 턴과 실제 heartbeat 턴을 구분한다.[^claude-loop][^claude-hooks]

확인할 항목은 예약 요청이 어떤 훅을 거치는지, 예약과 `turn_id`를 연결할 수 있는지, 만료 요청을 모델 실행 전에 막을 수 있는지다. `MessageDisplay`는 assistant 표시만 바꾸므로 사용자 프롬프트·빈 행·예약 안내까지 숨겨졌다고 가정하지 않는다.[^claude-hooks]

**완전 숨김 경로:** 구조화된 출력·resume 인터페이스를 이용해 Cache Keeper가 입력과 화면을 소유한다. 기존 네이티브 세션은 작업을 끝내고 안전하게 소유권을 넘긴 후 재개한다. 두 프로세스가 동시에 같은 기록에 쓰지 않는다.[^claude-headless]

설치 전부터 진행하던 세션을 다시 열 때 설정·도구·시작 정보가 바뀌어 prefix가 달라질 수 있으므로, 세션 ID 유지와 캐시 유지 효과는 별도로 검증한다.

### 9.2 Codex

공통 `LoopRunner`가 동일 `threadId`에 `turn/start`를 반복 호출한다. Cache Keeper가 App Server 클라이언트와 렌더러를 소유하며, 반환된 턴 ID로 유지용 이벤트만 제외한다.[^codex-server]

사용자가 복귀하면 활성 keeper 턴에 `turn/interrupt`를 요청하고 종료 이벤트를 확인한 다음 **별도의 실제 사용자 턴**을 시작한다. 사용자의 메시지를 유지용 턴에 `turn/steer`로 합치지 않는다.[^codex-server]

플러그인 훅은 설정·활동 감지·지원되는 도구 차단에 사용한다. `suppressOutput`으로 기본 Codex TUI의 출력을 숨기는 구현은 하지 않는다.[^codex-hooks]

### 9.3 Grok Build

네이티브 `/loop`는 즉시 첫 턴을 발생시킨다. 아직 캐시가 충분히 살아 있는 활성화 직후라면 이 호출이 불필요할 수 있으므로, 관리형 모드에서는 첫 필요 시각까지 기다리는 것을 기본으로 한다.[^grok-loop]

완전 숨김은 `grok agent stdio`의 ACP 이벤트를 렌더링하는 경로를 우선 검증한다. 해당 환경에서 기존 세션 로드가 가능한지 확인하고, 불가능하면 공식 headless resume 경로를 평가한다.[^grok-headless]

`session/prompt`와 `session/update` 사이의 완료 순서를 확인해야 한다. 턴 ID가 없으면 세션당 요청 하나만 허용하고 request별 소유권을 유지하되, 후행 이벤트를 시간 추정만으로 다음 사용자 턴에 귀속시키지 않는다. 확실한 경계를 얻지 못한 경로는 완전 숨김 지원으로 출시하지 않는다.

Grok의 수동 이벤트 출력으로 다음 턴을 실행하거나 응답을 숨기려 하지 않는다. 또한 스킬의 `allowed-tools`가 실제 도구 권한 제한이라고 가정하지 않는다.[^grok-hooks][^grok-plugins]

## 10. 사용자 입력과 동시성

### 사용자 입력 시 처리 순서

1. 입력 내용을 보존하고 새 keeper 실행을 잠근다.
2. 아직 제출 전인 tick은 취소한다.
3. 이미 진행 중인 keeper만 취소한다. 실제 사용자 턴은 취소하지 않는다.
4. 호스트의 종료 확인 후 사용자 메시지를 별도 실제 턴으로 제출한다.
5. 실제 답변을 표시하고, 원래 유지 기간이 남아 있으면 다음 유휴 시각부터 다시 대기한다.

취소가 불가능한 어댑터는 사용자의 입력을 보관한 채 기존 keeper 종료를 기다린다. 동시 실행으로 해결하지 않는다. 제한 시간 내 종료 확인이 되지 않으면 keeper를 비활성화하고 세션 상태를 사용자에게 알려준다.

### 안전장치

세션별 단일 소유자 잠금, activation별 `generation`, 요청별 `requestKey`를 사용한다. `off → on` 뒤 늦게 도착한 옛 이벤트가 새 keeper나 실제 사용자 메시지를 숨기지 못하게 한다.

일반 `Stop` 이벤트마다 새 유지 루프를 생성하지 않는다. keeper 자신의 완료 이벤트로 자기 자신을 다시 활성화하는 재귀 루프도 금지한다.

## 11. 최소 상태·어댑터 계약

아래는 구현 방향을 공유하기 위한 내부 타입 초안이다. 실제 SDK의 메서드명이나 스키마를 대신하지 않는다.

```typescript
type Host = "claude" | "codex" | "grok";
type Phase =
  | "off" | "armed" | "heartbeat" | "yielding"
  | "user_turn" | "paused" | "stopped";

interface KeeperState {
  host: Host;
  sessionId: string;
  generation: number;
  phase: Phase;
  activatedAt: number;
  expiresAt: number;
  intervalMs: number;
  ttlMs: number | null;
  lastRequestStartedAt: number | null;
  nextDueAt: number | null;
  activeRequestKey: string | null;
  lastVisibleAssistantMessageId: string | null;
  admittedTicks: number;
  maxTicks: number;
}

interface AdapterCapabilities {
  nativeLoop: boolean;
  existingSessionResume: boolean;
  trustedTurnCorrelation: boolean;
  preDispatchGuard: boolean;
  interrupt: boolean;
  liveDisplayControl: boolean;
  replayDisplayControl: boolean;
  cacheUsage: boolean;
  verifiedToolBlocking: boolean;
}
```

tick 시에는 `enabled → 소유권 → 종료 시각 → 사용자 활동 → 현재 턴 → 예산 → 다음 시각`을 검사하고, 세션 잠금 안에서 한 번 더 확인한 후 제출한다. 실패·타임아웃을 포함해 **제출된 요청은 횟수 상한에서 차감**한다.

요청 성공 시각과 캐시 사용 확인은 따로 저장한다. 응답 완료 시각만을 기준으로 TTL 시계를 새로 시작하지 않는다. 실제 캐시 타이밍은 공급자별로 확인한다.

## 12. 도구·비용·실패 제어

### 12.1 도구 비사용

정상 heartbeat에서 도구 사용은 0회를 목표로 한다. 가능한 경로에서는 keeper로 확실히 식별된 턴의 도구 실행을 호스트의 실행 직전 정책으로 차단한다. 이를 위해 매회 tool schema 자체를 제거·변경하지 않는 방식을 우선 검증한다.

다만 훅 하나가 모든 도구를 통제한다고 가정하지 않는다. Codex는 일부 hosted tool이 로컬 훅 경로 밖에 있으며, Grok 훅은 실패 시 도구 실행을 허용하는 동작이 문서화되어 있다.[^codex-hooks][^grok-hooks]

차단 범위를 확인하지 못한 경로는 “도구 실행 불가능”이라고 표시하지 않는다. 무인 실행을 기본 제공하기 전에 어댑터별 가드 테스트를 통과시킨다. 필요하면 안전한 관리형 경로로 한정한다.

### 12.2 횟수와 예산

초기 기본값은 `maxTicks = 120`, 최대 입력 기간은 24시간으로 제안한다. 짧은 주기로 긴 기간을 요청하면 횟수 상한이 먼저 종료시킬 수 있다는 점을 활성화 전에 표시한다.

```text
요청 기간: 12시간
반복 간격: 3분
횟수 상한: 120회
안내: 설정된 횟수 상한이 요청 기간보다 먼저 도달할 수 있음
```

비용 정보를 제공하는 호스트에서는 예상·실측 비용을 구분한다. 다음 요청의 보수적인 예상 비용을 예산에 예약할 수 없는 경로에서는 금액 상한을 엄격 보장이라고 부르지 않는다. 대신 하드 제한인 호출 횟수를 사용한다.

**최소 응답은 최소 총비용을 의미하지 않는다.** 입력 캐시 읽기·새 쓰기·일반 입력·출력 및 노출되는 reasoning 사용량을 함께 비교한다. 사용자에게 보여주는 `.`를 숨기는 것과 과금은 별개다.[^claude-cache][^openai-cache]

### 12.3 실패 정책

| 상황 | 동작 |
| --- | --- |
| 정상 `.` 응답 | 기본 화면 변화 없이 대기. 캐시 상태는 usage에 따라 별도 기록 |
| 다른 응답·도구 요청 | 즉시 pause. 보정 프롬프트 재시도 없음 |
| 인증 오류 | 중단하고 재인증 안내 |
| 사용량·속도 제한 | pause. TTL 유지를 명분으로 재시도하지 않음 |
| 네트워크 오류 | 연속 최대 2회 실패 후 pause. 즉시 반복 재시도 금지 |
| 모호한 요청 타임아웃 | 원 요청 종료를 확인하기 전 동일 요청 재전송 금지 |
| 만료·수동 off | 신규 제출 차단, 예약 제거, 진행 중 keeper 취소 시도 |
| 절전·단절 후 복귀 | 누락 요청 몰아 보내기 금지. 캐시 상태를 unknown으로 변경 |
| 세션·모델·작업 환경 변경 | 자동으로 새 세션을 따라가지 않고 pause |
| 식별·표시 필터 오류 | keeper 중지. 실제 대화를 보존하는 방향으로 처리 |
| 프로세스 재시작 | 기본적으로 유료 반복 요청 자동 재활성화 금지 |

## 13. 캐시 효과 관측

### 서로 다른 상태로 기록

| 상태 | 의미 |
| --- | --- |
| `request_ok` | 요청이 정상 종료됨 |
| `cache_observed` | 해당 요청에서 캐시 사용량이 실제 관측됨 |
| `cache_unknown` | 필요한 지표를 얻지 못함 |
| `gap_detected` | 유지가 끊겼을 가능성이 있는 시간 공백 |
| `paused` | 요청을 보내지 않는 상태 |

`cache_observed`도 “전체 대화가 계속 warm”이라는 뜻은 아니다. 과거의 관측값을 미래의 보장으로 표시하지 않는다.

수집 대상은 실제로 제공되는 캐시 읽기·쓰기 토큰, 일반 입력, 출력, reasoning, 지연, 비용이다. 공급자별 토큰 필드의 포함 관계가 다르므로 raw usage를 어댑터에서 정규화한다. 없는 값을 0으로 만들지 않는다.[^claude-cache][^openai-cache]

### 검증 실험

같은 모델·설정·규모의 대화에 대해 keeper를 끈 조건과 켠 조건을 비교한다. 실험 간 캐시 공유가 결과를 오염시키지 않게 분리하거나 충분한 만료 구간을 둔다. 비교 대상은 heartbeat 응답 자체보다 **유휴 후 실제 작업 요청**이다.

```text
대조군: 실제 작업 → 유휴 → 실제 다음 작업
실험군: 실제 작업 → 유휴 중 loop → 실제 다음 작업
```

캐시 읽기량, 쓰기량, 첫 응답 지연, 전체 비용, 다음 실제 답변의 작업 연속성을 비교한다. 일정한 hit 비율이나 절감률을 먼저 정해 놓고 달성했다고 가정하지 않는다.

CLI에서 지표를 얻지 못하는 조합은 반복 요청과 UI 기능만 검증 가능하다고 표시한다. API 문서에 필드가 있다는 이유만으로 구독형 CLI에서도 반드시 얻을 수 있다고 간주하지 않는다.

## 14. 저장·보안·기록

로컬 저장에는 세션 식별자, 턴 매핑, 실행 횟수, 시각, usage 요약을 우선 보관한다. 프롬프트·응답 원문과 인증 토큰은 플러그인이 별도로 복제하지 않는 것을 기본으로 한다.

숨김 이력 재표시에 필요한 매핑은 세션별로 저장하되, 사용자가 삭제할 수 있게 한다. 민감한 세션 기록은 호스트에 이미 남을 수 있음을 설명한다. 자체 파일은 사용자 전용 권한으로 만들고 외부 telemetry는 기본 비활성화한다.

같은 계정·정상 로그인 경로를 사용한다. 사용량 제한을 우회하기 위한 다중 계정 전환, 인증 정보 추출, 자동 승인 확대를 하지 않는다.

## 15. 개발 단계와 산출물

### Phase 0 — 호환성 시제품과 출시 경로 확정

세 플랫폼에서 짧은 heartbeat 한 번을 실행하고, 세션 연속성·턴 식별·표시 숨김·취소·캐시 지표를 각각 확인한다. 첫 단계부터 비용 상한을 둔다.

**산출물:** `compatibility-matrix.md`, 버전별 capability 결과, 익명화한 이벤트 fixture, 최소 화면 시제품.

**통과 조건:** 플랫폼별로 최소 하나의 “같은 세션 + 안전한 요청 소유권 + 숨김 표시” 경로 확보. 실패한 네이티브 경로를 완성된 기능처럼 취급하지 않는다.

### Phase 1 — 공통 실행기

상태 머신, 고정 종료 시각, 단일 세션 잠금, 사용자 입력 우선, tick 상한, stale-event 차단을 구현한다. 가짜 시계·가짜 호스트로 네트워크 없이 검증한다.

**산출물:** `core`, `loop-runner`, `local-store`, 단위 테스트.

**통과 조건:** 중첩 요청·만료 후 신규 제출·keeper 자기 재활성화가 모두 0회.

### Phase 2 — 표시 계층과 Claude 시제품

유지용 입력과 출력을 렌더링 전 필터링한다. Claude 표시 훅의 범위를 검증하고, 부족하면 관리형 출력 경로로 전환한다. 마지막 실제 답변·입력창·스크롤 보존을 구현한다.

**산출물:** 공통 화면, Claude 어댑터, live·replay 화면 테스트.

**통과 조건:** 정상 유지 턴이 기본 화면에 단 한 프레임도 노출되지 않음. 실제 `.` 메시지는 보존.

### Phase 3 — Codex 및 Grok 어댑터

Codex App Server의 턴 이벤트와 Grok ACP의 세션 이벤트를 공통 계약에 연결한다. 기존 세션 인계, 후행 이벤트, 취소 후 실제 입력 순서를 집중 검증한다.

**산출물:** 세 어댑터와 플랫폼별 설치 패키지·실행 안내.

**통과 조건:** 지원 경로에서 세 제품 모두 동일한 사용자 경험 제공. 네이티브 UI와 관리형 UI의 지원 범위를 분리 표기.

### Phase 4 — 캐시 효과·비용·내구성

실제 모델 호출로 대조 실험을 하고, 숨김 턴이 누적된 뒤에도 다음 실제 요청이 정상적으로 이어지는지 확인한다. 장시간 실행·절전·재시작·버전 변경을 테스트한다.

**산출물:** `validation-report.md`, 모델·인증·버전별 결과, 비용·usage 표시.

**통과 조건:** 캐시 효과에 관한 주장은 실험 결과 범위 안에서만 작성. UI 기능만 통과한 조합은 효과 미검증 표시.

### Phase 5 — 배포

설치·업데이트·제거 시 기존 설정을 보존하고, 제거 시 keeper 소유 예약만 취소한다. 사용자나 다른 플러그인의 loop를 삭제하지 않는다.

**산출물:** README, 플랫폼별 패키지, 진단 명령, 문제 해결 문서, 릴리스 체크리스트.

## 16. 테스트 매트릭스

| 테스트 | 기대 결과 |
| --- | --- |
| 정상 heartbeat 연속 실행 | 유지용 입력·응답·알림이 기본 화면에 나타나지 않음 |
| 사용자가 실제로 `.` 입력 | 정상 사용자 메시지로 보존 |
| 실제 답변이 `.` 또는 코드의 마침표 포함 | 삭제·손상 없음 |
| 응답 분할·공백·후행 이벤트 | 임시 노출 없이 올바른 턴으로 연결 |
| 실제 입력과 tick 동시 발생 | 사용자 우선. 같은 턴으로 합쳐지지 않음 |
| keeper 실행 도중 사용자 복귀 | 종료 확인 후 사용자 턴을 별도로 실행 |
| 만료 직전·직후·예약 큐 지연 | 만료 후 신규 유지 요청 0회 |
| off/on과 늦은 이전 이벤트 | generation이 다른 이벤트가 새 실행을 오염시키지 않음 |
| 훅·파서·표시 필터 오류 | keeper 중지. 실제 사용자 대화 손실 없음 |
| 예약 식별 불가 | 완전 숨김 네이티브 모드 활성화 거절 |
| 도구 요청·긴 응답 | 차단 가능한 경로에서는 실행 전 차단. keeper pause |
| 훅 실패·미지원 도구 경로 | 차단 보장 범위를 과장하지 않음. 안전 경로 재평가 |
| 두 프로세스가 같은 세션 사용 | 두 번째 keeper 소유권 획득 거절 |
| 두 세션·두 프로젝트 | 턴·예약·예산·화면이 서로 섞이지 않음 |
| 창 크기 변경·이력 재열기 | 숨김 유지와 실제 대화 앵커 보존 |
| 절전·단절·재시작 | catch-up 폭주·자동 유료 재활성화 없음 |
| 최대 tick·예산 도달 | 명시한 상한 정책대로 중단 |
| context 압축·모델 변경 | 상태 재평가. 과거 cache hit를 현재로 이어 표시하지 않음 |
| keeper 누적 후 “이어서 해줘” | 작업 연속성 평가. 실패 시 지원 범위·프롬프트 재검토 |
| 다른 기본 CLI에서 원본 이력 열기 | 숨김 범위 밖임을 문서화. 기록 삭제로 해결하지 않음 |

## 17. 제안 저장소 구조

```text
cache-keeper/
├── packages/
│   ├── core/                  # 상태·스케줄·잠금·예산
│   ├── runner/                # 로컬 프로세스와 세션 소유권
│   ├── ui/                    # 입력·표시 필터·이력·스크롤
│   ├── adapter-claude/
│   ├── adapter-codex/
│   └── adapter-grok/
├── plugins/
│   ├── claude/                # 호스트별 manifest·skills·hooks
│   ├── codex/
│   └── grok/
├── tests/
│   ├── unit/
│   ├── contracts/
│   ├── ui/
│   ├── integration/
│   └── fixtures/
└── docs/
    ├── development-plan.md
    ├── compatibility-matrix.md
    ├── validation-report.md
    ├── privacy.md
    └── troubleshooting.md
```

TypeScript 기반 공통 코어를 초기 선택으로 제안한다. 플랫폼 어댑터의 외부 스키마는 검증하고, SDK·CLI 버전은 테스트된 조합으로 고정한다. 실제 구현 전에 플러그인 manifest와 프로토콜 스키마를 설치 버전 기준으로 확인한다.

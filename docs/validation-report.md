# 검증 보고서 — 0.1.1

검증일: 2026-09-25, 한국 시간(Asia/Seoul). 환경: macOS arm64, Node 26.7.0.

추가 분석: [원본 로그 재감사와 유지 요청 포함 분석](cache-analysis.md)에서 Codex
24개 세션 중 20개에 최초 응답 이후 스킬 지시문이 추가된 것을 확인했습니다.
아래 캐시 수치는 그대로 유효한 관측값이지만, 초기 문맥 예열과 순수 만료 방지
효과가 섞여 있습니다. “환경 고정”은 검사한 실행 파일·설정 범위에 한정됩니다.

공개 설치 가능한 0.1.1 보완판의 검증 기록입니다. 캐시 효과는 아래 조건별 측정
범위에 한정됩니다. 실제 Mac의 절전·깨우기는 수행하지 않았습니다.

### 판정 기준

반복 요청이 성공하는지, 다음 사용자 요청이 캐시를 읽는지, 유지 요청까지 포함한
총사용 비용이 줄어드는지를 각각 검사했습니다. 캐시 읽기량이 늘었다는 사실만으로
비용 절감이나 전체 대화의 지속적인 캐시 유지를 입증하지 않습니다.

공급자 CLI의 비용 추정치는 구독 결제 금액과 다릅니다. 이번 검증에서는 구독 한도
소모량을 실험별로 분리한 계량값이나 실제 청구서의 차이를 얻지 못했습니다.

## 2. 실행 환경과 대조 방법

| 플랫폼 | CLI 버전 | 로그인된 구독 | 고정한 모델 |
| --- | --- | --- | --- |
| Claude Code | 2.1.282 | Claude.ai Max | `claude-opus-5-5[1m]` |
| Codex | 0.156.1 | ChatGPT Pro | `gpt-6-astra` |
| Grok Build | 1.0.41 | SuperGrok Heavy | `grok-4.7` |

기존 CLI 로그인으로 실행했습니다. 인증 토큰을 추출하거나 API 키를 새로 등록하지
않았습니다. 테스트는 합성 데이터와 임시 작업 폴더를 사용했으며 실제 작업 파일을
모델에 보내지 않았습니다.

각 조건은 **대조군·유지 기능 사용군 6쌍**으로 구성했습니다. 한 쌍은 같은 모델·설정·
작업 폴더·1,500행 데이터로 시작했습니다. 캐시가 대화 본문 전체를 공유하지 않도록
첫 사용자 메시지의 앞부분에 길이가 같은 서로 다른 확인용 문자열을 넣었습니다.
시스템·도구 프롬프트의 공통 앞부분은 여전히 캐시를 공유할 수 있습니다.

쌍마다 먼저 생성하는 실험군을 교대로 바꿨습니다. 초기 응답 완료 뒤 정해진 실제
유휴 시간이 지난 시점에 처음의 확인용 문자열을 물었습니다. 유지 기능 사용군에는
지정한 간격의 유지 요청만 추가했습니다. **시간을 가속하지 않았습니다.**

실험 중 런타임 파일의 SHA-256, CLI·Node 버전, 관련 설정 파일의 크기·수정 시각이
바뀌지 않았는지 확인했습니다. 설정 파일의 본문이나 인증 정보는 지문에 포함하지
않았습니다. 호스트가 추가하는 컨텍스트와 서버 라우팅까지 고정하지는 못했습니다.
결함 수정은 별도 후보 디렉터리에서 검증한 뒤 실험 종료 후 통합했습니다.

첫 응답 지연은 제출부터 **첫 화면 표시용 텍스트 조각**까지의 시간입니다. 내부
reasoning 시작 시각이나 순수 서버 추론 시간은 아닙니다. 완료 시간에는 로컬 CLI
처리도 포함됩니다. 표에는 유효한 6쌍의 중앙값을 사용하고 원자료에는 쌍별 값을 남깁니다.

캐시 읽기 비율의 분모는 Codex에서 캐시를 포함한 `inputTokens`, Claude·Grok에서
일반 입력 + 캐시 읽기 + 캐시 쓰기입니다. 제공되지 않은 값은 `null`로 보존했습니다.

조건별·쌍별 수치, 모든 유지 요청의 사용량, 중단한 실험, 장시간 실행 시각과 시각
보정 내역은 [0.1.1 측정 자료](measurements-0.1.1.json)에 있습니다.

## 3. 캐시와 비용 결과

| 플랫폼·유휴 시간·유지 간격 | 유효한 쌍 | 다음 요청의 캐시 읽기 비율: 대조군 → 사용군 | 유지 요청 포함 비용 추정치 변화의 중앙값 |

Claude는 6쌍 모두 마지막 사용자 요청의 캐시 읽기가 양쪽 **12,160토큰으로 동일**했습니다.
나머지 입력에 새 캐시 쓰기가 반복됐고, 유지 요청 1회를 추가한 사용군의 비용 추정치가
약 두 배였습니다. 이 조건에서 캐시 유지 개선이나 비용 절감은 확인되지 않았습니다.
같은 CLI 프로세스를 유지하는 방식과 MCP·설정 범위를 줄인 별도 진단에서도 새 쓰기가
반복됐습니다. 원인을 공급자 내부 동작으로 단정하거나, 전송 방식 변경만으로 해결됐다고
표시하지 않았습니다.

Grok의 12분 조건은 중앙값만 보면 양쪽 캐시 비율이 비슷합니다. 실제로는 대조군
6개 중 5개, 사용군 6개 중 4개에서 마지막 요청의 캐시 읽기가 관측됐습니다.
모든 쌍에서 유지 요청까지 포함한 비용이 늘어, 짧은 간격의 반복 호출이 경제적이라는
근거가 되지 않았습니다.

Grok의 70분 조건은 유지 요청을 **2회**로 줄였지만 6쌍 모두 비용이 늘었습니다.
마지막 요청에서 대조군은 모두 캐시 읽기가 0이었고, 사용군은 2개에서 약 99.7%,
1개에서 약 5.3%, 3개에서 0%였습니다. 일부 다음 요청에서 캐시 사용을 관측했지만,
지속적인 적중이나 유지 요청 비용을 회수하는 효과는 확인하지 못했습니다.

Codex의 35분·70분 조건에서는 다음 요청의 캐시 읽기 비율 개선이 관측됐습니다.
70분 조건의 사용군 6개는 모두 마지막 요청에서 약 99.5%의 캐시 읽기를 보고했습니다.
대조군은 4개 약 83.8%, 1개 약 40.2%, 1개 0%였습니다. 유지용 요청에도 입력·출력
사용량이 발생하므로, 이 개선을 총구독 사용량이나 비용 절감과 동일하게 해석하지 않습니다.

유의성을 주장하지 않습니다. 5개 조건의 30쌍은 모두 세션 연속성·유지 요청 완료·
환경 고정 검사를 통과했으며, 비용 절감에 성공한 표본만 고르지 않았습니다.

총비용 비교는 초기 데이터 입력 뒤 발생한 **모든 유지 요청과 마지막 사용자 요청**을
합칩니다. Claude는 CLI가 보고한 세션 누적 비용의 차이, Grok은 요청별 보고 비용의
합계를 사용합니다. Codex는 달러 비용을 제공하지 않아 비용 비교를 산출하지 않습니다.

Claude의 구독 포함 요청에 대한 공식 문서는 1시간 캐시 쓰기 TTL을 설명합니다.
이번 실행에서도 `ephemeral_1h_input_tokens`를 별도로 보존했습니다. 이는 요청의
캐시 쓰기 TTL 근거이며, 유휴 후 해당 대화 전체가 캐시에 남았다는 보장은 아닙니다.

캐시 적중은 공급자 측 라우팅과 퇴거 등의 영향을 받습니다. API 가격표를 구독형
CLI의 결제 금액으로 치환하지 않았습니다.

유지 요청 79회가 모두 정상 완료됐습니다. 실행 중 사용자 대화로 노출된 유지 이벤트,
동시 요청, 만료 뒤 신규 유지 제출은 없었습니다. 세 호스트의 종료 이벤트에
`reason: expired`가 기록됐습니다.

세 플랫폼의 별도 세션을 같은 시기에 시작했습니다. Claude는 50분 간격,
Codex·Grok은 3분 간격으로 실행했습니다. 30초마다 환경과 실행 상태를 확인하고,
유지 요청이 완료된 시각부터 다음 간격을 계산해 누락·중첩·몰아 보내기 여부를 검사했습니다.

2시간 종료 뒤에는 자동 비활성화, 만료 후 신규 유지 요청 차단, 이전 확인용 문자열의
정확한 회상, 원본 유지 턴 보존, 기본 이력에서의 숨김, 세션 재시작 후 꺼짐 상태와
후속 대화를 확인했습니다. 24시간 연속 실행까지 검증한 것으로 확대하지 않습니다.

### 시각 보정으로 발생한 검사 오류와 재평가

첫 최종 검사는 실패했습니다. 검사 코드가 간격을 일반 시각(`Date.now`)으로 계산해
0.23–0.25초 짧은 간격을 중첩으로 판정했습니다. 실제 요청끼리는 약 3분 또는 50분
떨어져 있었고, 실행기는 처음부터 단조 시계로 예약하고 있었습니다.

macOS `timed` 로그에서 **07:09:31에 −0.258071초**, **07:41:31에 +0.238991초**의
실제 시스템 시각 보정을 확인했습니다. 이 두 기록으로 저장된 시각을 같은 기준에
맞춘 뒤, **기존 허용 오차를 변경하지 않고** 모든 요청의 간격과 누락 여부를 다시
검사해 통과했습니다. 원래 실패 결과와 OS 보정 기록도 보존했습니다.

재실행용 검사 코드는 단조 시계 이벤트를 기록하도록 수정했고, 시각이 258ms 뒤로
보정되는 회귀 검사를 추가했습니다. 2시간 실험을 새로 반복한 것은 아닙니다.
초기 검사 실패로 실행기가 닫힌 뒤, 같은 원본 세션을 다시 열어 후속 회상·숨김·
꺼짐 상태를 검증했고, 한 번 더 재시작한 후의 회상도 확인했습니다.

장시간 실험은 코드가 고정된 상태에서 수행했습니다. 이후 세 가지 결함 수정을
통합한 최종 설치본에는 별도의 짧은 실제 호출·취소 회귀 검사를 적용했습니다.

## 5. 절전·단절·복귀

### 실제 프로세스 정지·재개: 통과

가짜 시계 없이 실제 Node 실행기에 `SIGSTOP`과 `SIGCONT`를 보냈습니다.

| 상황 | 실제 정지 시간 | 결과 |
| --- | ---: | --- |
| 유지 요청 진행 중 프로세스 정지·재개 | 약 11.5초 | 공백 감지, 진행 중 유지 요청 취소, 간격을 둔 재개; 즉시 몰아 보내기 없음 |
| 만료 시각을 넘긴 프로세스 정지·재개 | 약 6초 | 만료 처리, 신규 유지 요청 0회 |

어댑터는 가짜 호스트를 사용했습니다. 이 검사는 OS가 실행기 프로세스를 멈췄다
재개하는 상황을 검증하며, Mac 하드웨어의 실제 절전·깨우기 검사는 아닙니다.

### 브라우저 연결 단절·복귀: 통과

로컬 테스트 서버의 실제 스트림 소켓을 끊어 검사했습니다. 연결 복귀 후 작성 중인
문자열, 선택 영역, 읽고 있던 대화와 화면 위치, 30개 메시지를 그대로 보존했습니다.
기능을 끈 다음 다시 연결해도 자동 활성화와 사용자 입력 재전송이 없었습니다.
이 검사는 실제 브라우저와 가짜 호스트를 사용하며 모델 요청을 소비하지 않습니다.

### Mac의 실제 절전·깨우기: 미검증

현재 사용자가 직접 절전·깨우기를 수행할 수 없고, 관리자 권한 없이 안전한 자동
깨우기 예약을 설정할 수 없어 실행하지 않았습니다. 이 항목을 통과로 표시하지 않습니다.
후속 수동 검증 스크립트는 실제 `pmset`의 Sleep/Wake 기록이 없으면 통과를 거부합니다.

## 6. 발견한 결함과 수정

아래 수정은 실험 환경을 고정하기 위해 후보에서 검증한 뒤 마지막에 통합했습니다.

| 결함 | 수정 | 확인 방법 |
| --- | --- | --- |
| 실행기가 멈춘 동안 과거 캐시 관측이 남거나 만료 확인이 늦어질 수 있음 | 실제 시각과 단조 시계를 비교하는 감시, 공백 시 캐시 상태 초기화·진행 중 유지 취소·다음 주기 재설정 | 가짜 시계 경계 검사 + 실제 프로세스 정지·재개 |
| 브라우저 스트림이 끊어지면 연결이 복구되지 않음 | 제한된 재연결 간격과 대화 위치를 보존하는 스냅샷 반영 | 실제 소켓 단절 후 브라우저 조작 |
| Grok의 새 설치에 대화 이력 디렉터리가 없으면 첫 세션 시작 실패 | 없는 이력을 빈 이력으로 처리 | 디렉터리가 없는 상태의 회귀 검사 |
| 활성화 상태 저장 실패 후 사용자 턴 종료가 유료 반복 실행을 켤 수 있음 | 저장 완료 후에만 활성화, 실패하면 중지 상태 유지 | 저장 오류를 주입한 회귀 검사 |
| Claude의 1시간·5분 캐시 쓰기 구분이 정규화 중 사라짐 | 호스트가 제공한 TTL별 쓰기 사용량 보존 | 실제 응답 필드 + 정규화 회귀 검사 |
| 장시간 검사에서 OS 시각 보정을 요청 간격 오류로 판정 | 검사 시각을 단조 시계로 기록; 기존 자료는 실제 OS 보정 기록으로 재평가 | 동일 허용 오차 재검사 + 258ms 보정 회귀 검사 |

전체 자동 검사 31개와 최종 설치본의 실제 기능·취소 검사 6개 시나리오를 통과했습니다.
취소된 요청의 사용량은 확인할 수 없어 `null`로 남겼습니다. Claude의 엄격 모드
플러그인·마켓플레이스 검사와 Grok 자체 검사에도 오류·경고가 없었습니다.
브라우저 재연결 검증에 사용한 UI 코드와 최종 설치본의 UI 코드가 일치합니다.

인증·도구 차단은 기존 CLI의 정상 로그인과 플러그인의 거부 규칙을 사용했습니다.
승인 범위를 넓히거나 구독 제한을 우회하지 않았습니다. 원본 대화 이력은 보존합니다.

## 7. 재실행

소스 폴더 또는 배포 압축 파일을 푼 폴더에서 실행합니다. 배포 파일에 재현용 검사와
공개 측정 자료를 포함했습니다. 실제 호출은 아래처럼 명시적으로 사용량 소비를
선택해야 실행됩니다.

```sh
npm test
npm run check
npm run test:live -- --confirm-usage
npm run test:live -- --confirm-usage --cancel

# 실제 유휴 대조 실험: 70분, 유지 요청 2회, 6쌍
node tests/controlled-idle.mjs --confirm-usage --host grok \
  --model grok-4.7 --idle 70m --interval 25m --replicates 6

# 실제 2시간 연속 실행
node tests/endurance.mjs --confirm-usage --host codex \
  --model gpt-6-astra --duration 2h --interval 3m

# 실제 Mac을 직접 깨울 수 있을 때만 터미널에서 실행
node tests/manual-sleep.mjs --confirm-usage --host codex --model gpt-6-astra
```

실제 호출에는 구독 사용량이 발생합니다. 테스트 결과는 `test-results/`에 저장합니다.
공개 측정 데이터에서는 대화 본문과 세션·계정 식별자를 제외합니다. 원본 대화 기록은
각 호스트 CLI가 관리하며, 플러그인은 이를 수정·삭제하지 않습니다.

완전한 숨김은 cachemax 관리 화면의 기능입니다. 기존 기본 CLI는 종료한 뒤
세션을 인계해야 하며, 별도로 열린 기본 CLI까지 로컬 잠금에 참여시키지는 못합니다.
도구 차단의 지원 범위와 공개 설치 방법은 [호환성 표](compatibility-matrix.md)와
[README](../README.md)에 기록합니다. 이번 산출물은 공개 설치 가능한 패키지이며,
GitHub나 npm 레지스트리에 게시했다는 뜻은 아닙니다.

운영체제 검증은 macOS arm64에 한정됩니다. Linux·Windows, 이전 CLI 버전과 실제
24시간 실행은 검증하지 않았습니다. 기본 CLI의 내장 `/loop`만으로 완전 숨김을
제공하는 경로는 지원하지 않습니다.

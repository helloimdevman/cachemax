# 세 플랫폼 공통 조건 재관측 — 2026-09-25

이 관측은 이전 유지 문구를 사용했습니다. 이후의 [문구 축소 실측](usage-minimization.md)과
현재 코드의 기본 문구는 별도이며, 아래 원자료는 변경하지 않았습니다.

**이번 12분 유휴 조건에서는 세 플랫폼 모두 유지 요청의 경제적 이득을 확인하지
못했습니다.** Codex·Grok은 유지 기능을 끈 대조군도 마지막 요청에서 약 99.5~99.8%를
캐시로 읽었습니다. Claude는 예열 후에도 큰 캐시 쓰기가 반복됐습니다.

기존 기록 재분석에 이어 실제 대화를 새로 실행했습니다. 한국 시간 12:13:28~12:26:39,
플랫폼별 2쌍, 총 54회 대화 요청이 모두 완료됐습니다. 6쌍 모두 회상·유지 완료·환경
지문·단조 시계 간격 검사를 통과했습니다. 표본은 작으며, 이 통과는 기능·계측 기준의
통과입니다. 플랫폼 전체의 성능 순위나 캐시 정책의 인과 검증을 뜻하지 않습니다.

프로토콜·원자료·쌍별 계산·4시점 문맥 감사는
[재관측 측정 자료](reproducibility-measurements.json)에 함께 저장했습니다.
이전 [30쌍 분석](cache-analysis.md)과 실험 조건이 달라 통계 표본을 합치지 않았습니다.

**핵심 체크포인트: 유지 요청 자체의 사용량과 주기 준수**

사용자의 합격 기준은 ① 유지 요청이 거의 비용을 쓰지 않는가, ② 예정된 요청이
빠짐없이 실행되는가입니다. 복귀 요청의 캐시 비율이나 대조군 대비 비용 증가율만으로
이 두 기준을 판단하지 않습니다. 아래는 기존 54회 기록 중 **유지 요청 18회만**
다시 계산한 결과이며, 이번 재계산에는 모델 요청을 추가하지 않았습니다.

| 플랫폼, 각각 6회 | 회당 캐시 읽기 | 회당 일반 입력 / 새 캐시 쓰기 | 회당 출력 | 회당 CLI 비용 추정치 |
| --- | ---: | --- | ---: | ---: |
| Claude | 12,160 | 일반 2 / 쓰기 43,101~43,743 | 3 | $0.347308~0.352444 |
| Codex | 42,880 | 비캐시 196~257 / 쓰기 별도 미제공 | 5 | 미제공 |
| Grok | 적중 4회: 55,424~55,552; 미적중 2회: 0 | 일반 90~55,633 / 쓰기 0 | 22~38 | 적중 약 $0.0096; 미적중 약 $0.0379 |

요청은 `Only ".". No tools.`이고 정상 응답은 `.`입니다. 그러나 실제 입력에는
기존 대화·호스트 문맥이 포함됩니다. 짧은 출력만으로 전체 토큰 사용량이 작다는
판정을 내릴 수 없습니다. Claude의 일반 입력 2토큰만 세면 4.3만 토큰의 새 캐시
쓰기를 빠뜨리고, Codex의 비캐시 입력만 세면 42,880토큰의 캐시 읽기를 빠뜨립니다.
Grok의 출력 22~38토큰은 CLI 보고값이며 표시된 글자 수가 아닙니다. Grok의
추론 토큰 항목은 미제공이므로 그 차이를 추론 비용이라고 단정하지 않았습니다.

유지 6회의 비용 합계는 Claude $2.090608, Grok $0.11403328입니다. 회당 평균은
각각 $0.348435와 $0.019006입니다. 이 평균으로 **시간당 20회를 단순 환산**하면
약 $6.97와 $0.38입니다. 실제 1시간 실측이나 구독 청구액이 아니며, 응답 시간·미적중
비율·대화 길이가 바뀌면 값도 달라집니다. Codex의 비용 미제공은 0달러를 뜻하지 않습니다.

따라서 첫 기준은 아직 충족했다고 할 수 없습니다. Claude는 새 쓰기가 주요 개선
대상이고, Grok은 간헐적 미적중의 비용이 큽니다. Codex는 이번 유지 요청의 출력과
비캐시 입력이 작았지만 구독 한도 소모량·비용을 확인해야 합니다. 현재 제한은 유지
기간·횟수·타임아웃·도구 사용에 걸려 있으며, 토큰·달러 상한에 따른 자동 중지는 없습니다.

| 플랫폼 | 예정 / 제출 / 완료 | 예정 시각 대비 로컬 시작 지연 | 연속 요청의 시작 간격 |
| --- | --- | ---: | ---: |
| Claude | 6 / 6 / 6 | 1.93~5.09ms | 183.763~184.208초 |
| Codex | 6 / 6 / 6 | 1.14~5.61ms | 182.590~186.836초 |
| Grok | 6 / 6 / 6 | 1.69~5.59ms | 185.001~186.022초 |

두 번째 기준은 이번 실행 조건에서 통과했습니다. 유지 18회가 모두 완료됐고,
6개 사용군 세션의 단조 시계 주기 검사를 다시 통과했습니다. 중단·시간 공백 경고는
없었습니다. 지연의 기준은 첫 요청에서 활성화 + 180초, 이후에는
**직전 요청 완료 시각 + 180초**입니다. 시작 간격이 정확히 180초인 방식은 아닙니다. ms 값은 로컬 실행기의
요청 시작 계측이며 제공자 서버의 수신 시각을 측정한 값은 아닙니다.

실행 중에는 `cachemax status --host HOST --session ID`의 `nextDueAt`,
`intervalMs`, `admittedTicks`로 예약·제출 상태를 확인하고,
`cachemax logs --host HOST --session ID` 또는 화면의 **Activity**에서
`source: keeper`인 요청의 `startedAt`, `finishedAt`, `status`, `usage`와
`request_ok` 이벤트로 실제 완료를 확인합니다. `admittedTicks`는 완료 횟수가 아니고,
`cache_observed`는 전체 캐시 유지나 저비용을 보장하지 않습니다. 이 조회는 추가
모델 요청을 보내지 않습니다. 절전·프로세스 종료·네트워크 장애 중에도 호출된다는
보장은 이번 검사의 범위 밖입니다.

| 공통 조건 | 설정 |
| --- | --- |
| 최초 입력 | 동일한 1,500행 합성 데이터, 세션마다 다른 24자 확인 문자열 |
| 예열 | 양 군 각각 `Only ".". No tools.` 1회 |

| 반복 | 호스트별 2쌍, 먼저 준비하는 군을 교대로 변경 |

고정했습니다. CLI는 각각 2.1.282, 0.156.1, 1.0.41이며 이전 관측과 같습니다.
기존 로그인과 실제 호스트 설정을 사용했습니다. 모델·토크나이저·호스트가 붙이는
문맥은 서로 다르므로 플랫폼 간 원시 토큰 수나 절대 지연으로 순위를 매기지 않습니다.

이번 전체 실험의 CLI 추정치 합계는 Claude $6.2429436, Grok $0.42636408입니다.
Codex 달러 값은 `null`입니다. 같은 요청을 준비 비용과 유지 비용에 중복 합산하지 않았습니다.

Codex는 **스킬 목록 갱신을 유휴 전에 처리한 상태에서도, 이 짧은 조건에서는 유지가
추가적인 이득을 주지 않았습니다.** 네 세션 모두 같은 두 스킬 블록이 최초 턴과 예열
턴에 나타났고 이후에는 새로운 스킬 블록이 없었습니다. 대조군도 12분 뒤 높은 캐시
읽기를 보고했습니다. 예열 이후 합계는 다음과 같습니다.

| Codex, 2쌍 합계 | 대조군 | 사용군 |
| --- | ---: | ---: |
| 전체 입력 | 86,124 | 344,932 |
| 비캐시 입력 | 364 | 1,764 |
| 캐시 읽기 | 85,760 | 343,168 |

비캐시 입력과 캐시 읽기가 모두 늘었습니다. 캐시 적중률이 약 99.5%여도 추가 호출
3회의 입력 부담은 남습니다. 첫 표시 지연도 두 쌍에서 각각 0.939초, 4.098초
늘었습니다. 이것만으로 일반적인 속도 저하를 주장하지는 않습니다. 높은 적중이
개별 요청의 빠른 표시를 보장하지 않는다는 사례로 해석합니다.

**이번 12분 결과와 이전 35·70분 결과의 차이를 예열 하나의 효과로 단정할 수는
없습니다. 유휴 시간도 바뀌었습니다.** 35·70분에서 초기 문맥 추가 효과와 실제
만료 방지 효과를 분리하려면 같은 예열 조건으로 그 유휴 시간을 다시 측정해야 합니다.

Claude의 캐시 읽기는 마지막 요청 네 개와 유지 요청 여섯 개 모두 12,160토큰입니다.
예열 이후 캐시 쓰기 합계는 대조군 86,761토큰, 사용군 347,177토큰입니다.
이전 70분 조건에서 관측한 큰 새 쓰기가 이번 짧은 간격에서도 반복됐습니다.
유지 간격만 줄여 해결된다는 근거는 얻지 못했습니다.

Claude 원본 로그에서는 `deferred_tools_delta`, `mcp_instructions_delta`의
등장 시점·내용이 일부 세션에서 달랐고 유휴 이후에도 추가됐습니다. 동일한 설정
파일 지문이 실제 요청 문맥의 동일성을 보장하지 않는 사례입니다. 다만 관측한
첨부 문맥은 전체 전송 요청이 아니므로, 이 변화만으로 캐시 쓰기 반복의 원인을
확정하지 않았습니다. 다음 진단은 요청 앞부분·도구 정의·캐시 경계의 변화를 구분하는 것입니다.

Grok은 마지막 요청 네 개 모두 높은 캐시 읽기를 보고했지만, 유지 과정은 달랐습니다.

| Grok 사용군 | 유지 1 → 2 → 3의 캐시 읽기 토큰 | 마지막 사용자 요청 읽기 |
| --- | --- | ---: |
| 쌍 0 | 55,424 → 55,552 → 55,552 | 55,680 |
| 쌍 1 | 55,424 → 0 → 0 | 55,552 |

쌍 1의 두 미적중이 비용 증가를 크게 만들었습니다. 첫 수동 감사부터 마지막 감사까지
기록된 system·합성 문맥의 해시는 변하지 않았습니다. 따라서 관측한 문맥 블록의
변화로 이 두 미적중을 설명할 수는 없습니다. 서버 라우팅·퇴거 또는 기록되지 않은
요청 차이는 여전히 미확인입니다. 한 세션에만 초기 MCP 연결 중 알림이 추가된
차이도 있어, 양 군의 전체 요청이 완전히 같았다고 주장하지 않습니다.

기존 관측과의 비교는 다음 범위에서 유효합니다.

| 플랫폼 | 이번에 다시 관측한 현상 | 아직 확인하지 못한 부분 |
| --- | --- | --- |

시간 계측은 `performance.now()`를 사용했습니다. 복귀 요청은 목표 유휴 시간보다
약 11~65ms 뒤에 제출됐으며, 모든 유지 간격 검사를 통과했습니다. 전체 54회가
완료 상태이고 자동 재시도·대체 표본 추가는 없었습니다. 종료 후 12개 세션의 실행기
잠금과 가드 파일이 해제됐는지도 확인했습니다.

공통 예열 옵션, 준비 단계 사용량 보존, 진행 중 관측 저장, 기존 결과 파일 덮어쓰기
방지, 단조 시계 검사를 기존 실험기에 추가했습니다. 문맥 감사는 선택한 합성 세션의
원본 로그만 읽고 해시·크기·종류를 내보냅니다. 프롬프트 본문·세션 ID·인증 정보는
공개 자료에 포함하지 않았습니다. 런타임 플러그인과 설치본은 바꾸지 않았습니다.

경계 진단, Grok 라우팅 메타데이터 확인입니다. 현재 자료는 기본 유지 빈도를 높이거나
경제적 절감을 약속할 근거가 되지 않습니다.

```sh
# 저장된 자료만 재계산: 추가 모델 요청 없음
node scripts/summarize-validation.mjs docs/reproducibility-measurements.json
node --test tests/validation.test.mjs

# 같은 조건으로 새 실측: 호스트별 최대 18회, 구독 사용량 발생
# --label은 아직 존재하지 않는 이름으로 바꿉니다.
node tests/controlled-idle.mjs --confirm-usage --host codex --model gpt-6-astra \
  --idle 12m --interval 3m --replicates 2 --warmup --label fresh-codex-run
```

Claude는 `--host claude --model 'claude-opus-5-5[1m]'`, Grok은
`--host grok --model grok-4.7`로 같은 옵션을 사용합니다. 세 호스트를 모두 실행하면
최대 54회입니다. 원본 실험 상태 폴더가 남아 있다면 `scripts/audit-host-context.mjs`에
호스트별 상태 루트를 담은 로컬 JSON을 전달해 문맥 감사를 다시 할 수 있습니다.
자동 검사 33개도 모두 통과했습니다.
